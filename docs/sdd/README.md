# SDD. Поведение агента и контракты инструментов

Эта спецификация фиксирует поведение реализованного прототипа для приёмки.
Проверки внешней модели отмечены как ручные. Автотесты проверяют контракты
и переходы состояния с подменёнными внешними сервисами.

## Контекст и границы

Стажёр входит в приложение и работает через чат. Backend сохраняет вопрос
и отправляет в ML идентификаторы пользователя и сообщения. ML читает историю
этого пользователя, ограниченную указанным сообщением, и передаёт в модель
подходящие фрагменты PostgreSQL. База документов общая для вошедших пользователей.
Демо-страницы MCP хранятся отдельно и могут ограничивать доступ по ID пользователя.

LLM получает только разрешённые инструменты чтения и подготовки черновиков.
MCP проверяет Bearer-токен и ID пользователя. Чтение черновика или статуса
ограничено его владельцем. Для отправки и демо-согласования нужен отдельный
токен. Корпоративные действия имитируются внутри проекта.

## Сценарии и условия приёмки

| ID | Запрос и предусловие | Ожидаемое поведение |
| --- | --- | --- |
| KB-01 | Стажёр спрашивает, что такое OKR, после `make seed`. | Агент использует найденный фрагмент основной базы и объясняет цель и ключевой результат. Пустой поиск MCP не отменяет найденный фрагмент. |
| KB-02 | В переданном контексте нет ответа на вопрос. | Агент обозначает нехватку сведений в контексте. Наличие документа во всей базе остаётся неизвестным. |
| ACC-01 | Стажёр просит доступ на чтение `CAT-DEV` и сообщает рабочее обоснование. | Агент проверяет ресурс, показывает уровень, согласующего и сохранённый черновик с ID и версией. После отдельного подтверждения возвращает номер и статус ожидания. |
| REV-01 | Стажёр просит ревью PR №41. | Агент сообщает о красном CI и проверке `unit-tests`. Черновик ревью для такого PR не создаётся. |
| REV-02 | Стажёр просит ревью PR №42 и выбирает `demo-reviewer`. | Агент показывает commit и ревьюера в черновике. При подтверждении MCP перепроверяет параметры и возвращает номер операции или просит пересоздать черновик, если условия изменились. |
| ABS-01 | Стажёр просит краткое отсутствие. | Агент уточняет начало, конец и часовой пояс. Для корректного интервала показывает черновик. После подтверждения возвращает статус ожидания либо сообщает о пересечении. |
| SAFE-01 | Пользователь не подтвердил заявку точной командой либо указал чужой черновик. | Отправка не выполняется. Чужой черновик недоступен. |
| SSE-01 | Стажёр отправляет обычный вопрос. | Интерфейс показывает ожидание, принимает фрагменты `token`, завершает ответ по `done` и обновляет историю. Ошибка обработки отображается в чате. |

## Контракты MCP

| Семейство | Вход и назначение | Результат |
| --- | --- | --- |
| `knowledge_search`, `knowledge_get_page` | Поисковый запрос или ID страницы. | Доступные пользователю демо-материалы, раздел и ссылка при наличии. |
| `access_inspect`, `access_prepare`, `access_get_request` | Ресурс, обоснование для черновика или ID заявки. | Условия доступа, черновик или состояние своей заявки. |
| `pull_request_inspect`, `review_prepare`, `review_get_status` | Номер PR, выбранный ревьюер для черновика. | CI, commit, список допустимых ревьюеров, черновик или история своих запросов. |
| `absence_options`, `absence_prepare`, `absence_get_request` | Для черновика нужны тип `short_leave` и две даты ISO 8601 с часовым поясом. | Правила, черновик либо статус своей заявки. |
| `action_get_draft`, `*_submit` | ID черновика и версия при отправке. Сервер ML разбирает отдельное сообщение `Подтверждаю <id> <версия>`. | Подтверждённый результат, отказ по проверке или сообщение о недоступности. |
| `access_demo_approve` | Команда `демо согласовать <номер заявки>` для своей тестовой заявки. | Тестовый статус согласования. |

Состояние черновика начинается с `awaiting_confirmation`. Отправка валидной
заявки на доступ или отсутствие переводит её в `pending_approval`, а запрос
ревью — в `review_requested`. Повторное подтверждение сохранённой операции
возвращает существующий результат. Ответ об отправке формируется по результату
инструмента. Исходные схемы параметров находятся в [роутерах MCP](../../ml/src/mcp/routers).

## Проверки

- Контекст, поток и обработка ошибок проверяются в [test_chat.py](../../ml/tests/test_chat.py)
  и [test_model_api.py](../../ml/tests/test_model_api.py).
- Контракты, доступ и переходы заявок проверяются в [test_mcp_actions.py](../../ml/tests/test_mcp_actions.py)
  и [test_mcp_client.py](../../ml/tests/test_mcp_client.py).
- Проверка поведения с реальным провайдером проводится вручную по
  [шагам демо](../../README.md#порядок-проверки-демо).
