# AI Buddy для нового разработчика

AI Buddy — это приложение для знакомства с проектом и поиска информации в материалах команды. В репозитории есть веб-интерфейс, сервер на Go, отдельный сервис обработки документов на Python и общая база PostgreSQL. Если ты только начинаешь работу, сначала открой локальный предпросмотр и посмотри, как выглядит чат. Затем подними окружение через Docker Compose и проследи, как браузер получает собранный интерфейс, куда направляются запросы и откуда сервис документов получает данные. Эти два способа запуска полезны в разных ситуациях и спокойно сосуществуют на одной машине.

Начни с **текущей ветки**. В совместном репозитории инструкция из задачи, файлы приложения и код соседней ветки могут описывать разные стадии одной функции. _Сверяй команды с тем коммитом, который запускаешь._ Особенно это важно для авторизации и чата. В этой версии фронтенд содержит клиент для истории и отправки сообщений, однако в серверном маршрутизаторе этой ветки публичный `/api/chat` ещё не зарегистрирован. Локальная демонстрация позволяет увидеть потоковый интерфейс независимо от этой интеграции.

> Если цель — проверить отступы, Markdown, прокрутку или анимацию ответа, достаточно Vite и локального предпросмотра. Полное окружение полезно для проверки контейнеров, миграций и границ между сервисами.

## 1. Карта репозитория

- **`frontend/`** — клиентское приложение.
  - `src/pages/` содержит страницы, включая лендинг и чат в текущей ветке.
  - `src/shared/` содержит общие компоненты и обёртку над HTTP-запросами.
    - `src/shared/ui/` — логотип, кнопки, модальные окна и иконки.
    - `src/shared/api/` — общая логика запросов и представление HTTP-ошибок.
  - `src/entities/session/` описывает получение текущей сессии для маршрутизации.
- **`backend/`** — HTTP-сервер на Go и Gin.
- **`ml/`** — сервис документов на Python с FastAPI.
  - `src/features/documents/` содержит обработку документов, разбиение текста, получение векторов и запись результатов.
  - `tests/` содержит тесты обработки и хранения.
- **`infra/postgres/`** — SQL-миграции базы.
- **`nginx/`** и **`docker-compose.yml`** — настройки входной точки и локального окружения.

Названия директорий помогают быстро выбрать, где искать причину. Если отступы отличаются между сообщениями с обычным текстом и сообщениями с кодом, начни с CSS страницы чата и проверь фактическую структуру элементов в DevTools. Если Vite проксирует запрос на неожиданный адрес, проверь `frontend/.env.local` и конфигурацию Vite. Если контейнер обработки документов возвращает ошибку, смотри логи `ml`, затем состояние базы и мигратора. Такая последовательность сокращает число мест, в которых приходится одновременно держать контекст, и позволяет воспроизвести проблему на минимальной части системы.

### Какие технологии здесь используются

| Слой                   | Технологии                                | Где смотреть в коде                                        |
| ---------------------- | ----------------------------------------- | ---------------------------------------------------------- |
| Веб-интерфейс          | React 19, TypeScript, Vite                | `frontend/package.json`                                    |
| Маршрутизация и данные | TanStack Router, TanStack Query           | `frontend/src/router.ts`, `frontend/src/entities/session/` |
| Представление Markdown | `react-markdown`, CSS Modules             | `frontend/src/pages/chat/`                                 |
| HTTP-сервер            | Go, Gin                                   | `backend/internal/server/server.go`                        |
| Сервис документов      | Python, FastAPI, Uvicorn, asyncpg         | `ml/requirements.txt`, `ml/src/main.py`                    |
| Хранение               | PostgreSQL и расширение pgvector          | `infra/postgres/`                                          |
| Локальное окружение    | Docker Compose, nginx, отдельный мигратор | `docker-compose.yml`, `nginx/default.conf`                 |

За маршруты отвечает TanStack Router, а за загрузку и кэширование серверных данных — TanStack Query. Это разделение видно по точкам входа. Маршрутизатор решает, какую страницу показать с учётом сессии. Компонент чата загружает историю и отдельно ведёт состояние текущей отправки. Уже на уровне отдельного сообщения исходная строка становится HTML-разметкой через `react-markdown`. Если хочется понять, почему вопрос в ленте появляется раньше ответа, полезно прочитать компонент в этом порядке, от состояния отправки к списку сообщений и затем к рендереру одного элемента.

### Что делает nginx

В Compose nginx публикует порт `80` на локальной машине. Для обычного запроса он отдаёт статические файлы собранного фронтенда. Правило `try_files` возвращает `index.html` для маршрута SPA, поэтому браузер может открыть путь напрямую, а клиентский маршрутизатор затем решает, есть ли к нему доступ. Запросы, начинающиеся с `/api/`, nginx пересылает сервису `backend` на его внутренний порт `8080`. В режиме разработки аналогичное направление для запросов `/api` задаёт прокси Vite.

#### Внутренний адрес и адрес браузера

Имена `backend`, `postgres` и `ml` принадлежат сети Compose. Они удобны в настройках контейнеров. Браузер на машине разработчика обращается к опубликованному адресу, например `http://localhost` для nginx или к адресу, который напечатал Vite. Сервис документов слушает `8000` внутри контейнера, а конфигурация Compose этой ветки не публикует этот порт на хосте. Поэтому пример запроса к внутреннему маршруту нельзя механически превращать в браузерный URL. При проверке всегда записывай, **откуда** отправлен запрос и **через какой адрес** он должен пройти.

## 2. Быстрый старт с фронтендом

Если задача связана с интерфейсом, начни с запуска Vite. В Dockerfile фронтенда используется Node.js 24, поэтому для воспроизводимости удобно взять ту же основную версию. Установка через `npm ci` использует версии из lock-файла. Команда разработки запускает сборку по запросу и подхватывает изменения в файлах. После старта ориентируйся на адрес в терминале: когда обычный порт занят, Vite может выбрать другой.

1. Открой терминал в корне репозитория.
2. Перейди в `frontend` и установи зависимости.
3. Запусти сервер разработки.
4. Открой `/chat-preview.html` или `/chat-preview.html?demo=1` на адресе этого сервера.

```bash
cd frontend
npm ci
npm run dev -- --host 127.0.0.1
```

Обычный предпросмотр начинается с пустой истории. Демонстрационный параметр добавляет сообщения из визуального референса. В обоих режимах можно отправить сообщение и увидеть локальную имитацию ответа. Для длинного сценария в демонстрационном режиме отправь вопрос «Как устроен проект AI Buddy, как запустить его локально и какие технологии используются?». После завершения можно отправить его снова в той же вкладке. Предпросмотр позволяет проверять переход между пустым состоянием, ожиданием, появлением фрагментов и итоговым ответом без подготовленной серверной сессии.

### Проверка рабочего маршрута

У рабочего `/chat` действует проверка сессии. Он входит в группу маршрутов, доступных авторизованному пользователю. В текущем фронтенде проверка пользователя обращается к `GET /api/user`, а при отсутствии сессии маршрутизатор отправляет гостя на `/welcome`. Поэтому переход на рабочий маршрут и открытие HTML-предпросмотра дают разные результаты. Если при разработке с локальным backend нужно изменить адрес прокси, сверяй значение `API_PROXY_TARGET` с [шаблоном окружения фронтенда](https://github.com/pivoslavik/giga-buddy/blob/main/frontend/.env.example). Для просмотра анимаций достаточно HTML-предпросмотра.

#### Команды повседневной проверки

```bash
npm test
npm run lint
npm run build
```

Запускай эти команды из `frontend`. Тесты используют Vitest и Testing Library, линтер — ESLint, а сборка сначала проверяет TypeScript и затем формирует `dist` через Vite. Для визуальных изменений полезно выполнить отдельную ручную проверку в браузере: тесты могут подтвердить, что код стал элементом `pre`, но размеры этого элемента, его полосу прокрутки и состояние при узком экране удобнее наблюдать на реальной странице. Инструкцию по переменным, скриптам и структуре смотри в [README фронтенда](https://github.com/pivoslavik/giga-buddy/blob/main/frontend/README.md).

## 3. Запуск контейнеров через Docker Compose

Используй полный стек, если нужно проверить локальную базу, миграции или сборку приложения в тех же образах, которые описаны в проекте. Для запуска нужен работающий Docker с Compose. Из корня проекта подготовь файл `.env` по образцу `.env.example` и проверь значения `DB_NAME`, `DB_USER` и `DB_USER_PASSWORD`. Пример содержит локальные значения для старта. Фактический пароль держи в локальном окружении. Если файл уже существует, проверь его перед запуском и сохрани текущие настройки.

```bash
# Выполнять из корня репозитория в Bash.
test -f .env || cp .env.example .env
docker compose up -d --build
docker compose ps -a
docker compose logs --tail=80 nginx backend ml migrator
```

Сначала посмотри список контейнеров, включая завершившиеся. `migrator` выполняет миграции, а `frontend` собирает статические файлы в общий том. Их успешное завершение ожидаемо. Backend ждёт готовности PostgreSQL и успешной миграции. Nginx запускается после успешной сборки фронтенда и проверки здоровья backend. Контейнер `ml` стартует после миграций и готовит соединения с базой и модель эмбеддингов. Первоначальная сборка и инициализация могут занять больше времени, чем последующие запуски, поэтому состояние контейнеров и последние строки логов полезнее простой повторной команды запуска.

### Первый проход по диагностике

1. Убедись, что запущен Docker, а опубликованный порт nginx свободен.
2. Сверь имена сервисов в `docker compose ps -a` с файлом Compose.
3. Проверь, успешно ли завершились `migrator` и сборка `frontend`.
4. Проверь доступность nginx по локальному адресу.
5. Сопоставь ошибку в браузере с логами сервиса, который должен обработать запрос.

В этой ветке у backend реализован `GET /health`. Healthcheck в Compose проверяет его по адресу `http://127.0.0.1:8080/health` внутри контейнера. Именно этот контекст важен при чтении логов. Если доступ к статическому интерфейсу уже работает, проверь отдельно, что ожидаемый API-маршрут зарегистрирован в выбранной ветке. Статическая страница, состояние backend и наличие конкретного обработчика представляют собой разные этапы проверки. Когда несколько этапов объединены в одну гипотезу, появляется соблазн менять прокси, хотя запрос уже дошёл до приложения и получил обычный ответ об отсутствующем маршруте.

> Для локальной проверки сохрани вывод `docker compose ps -a` и первые относящиеся к проблеме строки логов. Этого обычно достаточно, чтобы другой разработчик понял, где прервался запуск.

### Какие данные переживают перезапуск

Том `postgres_data` хранит данные PostgreSQL. Том `frontend_static` используется для артефактов сборки, которые читает nginx. Если обновился интерфейс, сначала проверь, действительно ли контейнер фронтенда завершил новую сборку. Если изменилось устройство таблицы, посмотри, какая миграция применена и какой экземпляр базы читает нужный сервис. **Сохраняй локальные данные**, особенно если перед этим вручную добавлял материалы для проверки. Для просмотра статуса, чтения логов и просмотра схемы достаточно диагностических команд, не затрагивающих содержимое томов.

## 4. Как индексируются документы

Документы лежат в таблице `documents`. В миграциях видны поля идентификатора, заголовка, описания, текста и категории. Сервис на Python принимает запрос на обработку документа по идентификатору, получает текст, разбивает его на фрагменты, создаёт эмбеддинги и записывает фрагменты с порядковыми номерами в `document_chunks`. В этой ветке обработчик доступен внутри сервиса `ml` как `POST /documents`. Модель из конфигурации обработки — `intfloat/multilingual-e5-small`, а миграция хранит векторы размерности `384`.

### Что означает идентификатор в запросе

Пример тела запроса для **внутреннего** обработчика сервиса документов:

```json
{
  "document_id": 42
}
```

Значение `42` здесь условное. При реальном вызове нужен идентификатор существующего документа. Схема проверяет положительное целое число и отклоняет дополнительные поля. Успешный результат содержит `id` и `chunk_count`. Обработчик различает отсутствующий документ, пустой текст, изменение документа во время обработки и недоступность вычислений или базы. При диагностике сохраняй точный HTTP-статус и исходный идентификатор. Два запроса с одинаково кратким сообщением об ошибке могут иметь разные причины, если один не нашёл запись, а другой достиг этапа вычисления эмбеддингов.

#### Как посмотреть разбиение текста отдельно

Следующий короткий пример можно запустить из каталога `ml` в окружении с зависимостями сервиса. Он использует существующий класс `Chunker` и помогает посмотреть результат на небольшом тексте перед тем, как отлаживать весь процесс.

```python
from src.features.documents.chunker import Chunker

document = (
    "Перед первым запуском проверь настройки окружения.\n\n"
    "Если тестируешь только интерфейс, открой локальный предпросмотр чата."
)

for index, chunk in enumerate(Chunker().split(document)):
    print(f"{index}: {chunk}")
```

Небольшой пример особенно полезен для проверки нормализации текста. `Chunker` сводит последовательности пробельных символов к одному пробелу. По умолчанию размер фрагмента составляет 450 символов, а перекрытие — 75. Попробуй подать сначала одну короткую строку, затем текст с пустой строкой между абзацами, а потом более длинный фрагмент. Сравни результат с тестами в `ml/tests/test_chunker.py`. При разборе проблемы с качеством индексации фиксируй исходный текст и результат разбиения отдельно: так легче понять, на каком этапе исчез контекст, и повторить проверку с теми же входными данными.

### Проверка результатов в PostgreSQL

Если есть подключение к локальной базе, начни с выборки, которая только читает данные. Для небольшого обзора достаточно идентификатора, заголовка и категории. Чтобы сопоставить документ с фрагментами, соединяй таблицы по `document_id` и сортируй по `chunk_index`. Это полезнее, чем ориентироваться на порядок, в котором строки случайно вернул запрос.

```sql
SELECT id, title, category
FROM documents
ORDER BY id
LIMIT 5;

SELECT d.id AS document_id, d.title AS document_title, d.category AS document_category, c.chunk_index AS chunk_number, char_length(c.content) AS content_length, left(c.content, 120) AS content_preview FROM documents AS d JOIN document_chunks AS c ON c.document_id = d.id ORDER BY d.id, c.chunk_index LIMIT 20;
```

Вторая выборка специально оставлена длинной, чтобы в чате было видно, как прокручивается строка внутри блока кода. Она выводит короткий фрагмент содержимого и сохраняет читабельный порядок результатов. В реальной работе длинный SQL удобно разнести по строкам по частям запроса. Если запрос возвращает пустой набор, сначала проверь, есть ли документы, затем наличие фрагментов для нужного идентификатора, и только после этого логи сервиса. Наличие строки в `documents` показывает, что текст сохранён, а наличие строк в `document_chunks` показывает отдельный этап работы.

## 5. Как устроен чат во фронтенде

В текущей ветке страница получает историю через клиентский транспорт и передаёт сообщения компоненту отображения. Пока история загружается, виден статус загрузки. Успешный пустой ответ показывает приглашение написать первое сообщение. При ошибке загрузки есть сообщение об ошибке и повторная попытка. После отправки вопрос отображается сразу как ожидающий сохранения, а временный ответ ассистента растёт по мере поступления фрагментов. Когда поток завершён, интерфейс обновляет историю и показывает сохранённый ответ.

### Почему предпросмотр подходит для отладки потока

Локальный транспорт вызывает тот же `onDelta`, который принимает компонент чата. Он использует заданную переписку только в демонстрационном режиме и хранит результат отправки в памяти страницы. Реальный API-клиент умеет читать кадры SSE и перечитывает историю после завершения потока, однако формат прикладных событий публичного сервера ещё не подключён к `onDelta` в этой ветке. Благодаря изоляции предпросмотра можно изучать поведение интерфейса на повторяемых фрагментах текста, пока серверный контракт развивается отдельно.

```typescript
type PreviewDelta = (fragment: string) => void

function replayExample(onDelta: PreviewDelta) {
  const fragments = ["Проверяем ", "границы фрагментов ", "и итоговую строку."]

  for (const fragment of fragments) {
    onDelta(fragment)
  }
}

let displayedText = ""
replayExample((fragment) => {
  displayedText += fragment
})
```

Это маленькая модель накопления строки. В самом предпросмотре фрагменты подаются с интервалом, чтобы можно было наблюдать эффекты. В интерфейсе каждый новый фрагмент начинает проявляться сразу. Когда очередные символы закрывают выделение, ссылку или блок кода, Markdown пересобирает структуру ответа, а уже показанные фрагменты сохраняют своё время появления. Поэтому полезно тестировать **несколько соседних фрагментов** и длинные абзацы: ошибка может проявиться только в момент, когда видимое представление уже полученного текста меняется из-за новой закрывающей последовательности.

### Примеры, которые удобно искать глазами

- **Выделение** отмечает ключевые действия.
  - _Курсив_ подходит для замечаний, которые не должны теряться в инструкции.
  - _**Жирный курсив**_ выделяет шаг, важный для воспроизведения.
  - ~~Перезапускать все контейнеры при любой ошибке~~ — привычка, которую лучше заменить проверкой конкретного сервиса.
- Inline-код показывает, где важны точные символы: `npm run dev`, `onDelta`, `chunk_index`.
- В обычном тексте экранирование сохраняет буквальные знаки: \*звёздочки\*, \_подчёркивания\_, \[квадратные скобки\], \#решётку и \|вертикальную черту\|.

Текущий рендерер читает CommonMark. В этой сборке таблица с вертикальными чертами, чек-лист и зачёркивание остаются полезными диагностическими образцами: по ним видно, что именно происходит с исходным Markdown в текущем интерфейсе. Язык блока кода сохраняется в разметке, а строка отображается моноширинным шрифтом. Кнопка «Копировать» переносит исходный Markdown всего ответа, включая границы блоков. При проверке буфера обмена вставь содержимое в текстовый редактор и сверь начало, выбранный блок кода и последний абзац.

#### Как сравнить широкий и узкий экран

На широком экране сначала прокрути ответ до таблицы и посмотри, на каких строках заканчиваются длинные названия технологий. Потом уменьши ширину окна и повтори этот шаг. При переносе строки ориентирами остаются подписи столбцов в исходном тексте и названия разделов. Если колонка или длинное имя выходит за пределы пузыря, сравни ширину самого сообщения, ширину области истории и ширину всего документа. Это три разные области. Строка внутри блока SQL может требовать горизонтальной прокрутки, а поле отправки должно оставаться доступным на ширине экрана.

Для вложенных списков удобно начать с пункта про `frontend/`: внутри него есть два уровня и элементы с коротким inline-кодом. Проверь, видно ли различие между подчинённым пунктом и следующим разделом основного списка. В цитате важны переносы и положение полосы слева, а у ссылки полезно проверить и читаемость подписи, и фактический адрес. Повтори один и тот же переход сначала во время генерации, а затем в сохранённом ответе. Так проще заметить, если граница фрагмента потока повлияла на отображение, хотя исходный текст по завершении выглядит правильно. Для воспроизведения выбери одну ширину окна и зафиксируй её вместе с названием раздела.

Для ручной проверки сначала дождись появления двух абзацев и прокрути ленту чуть вверх. Убедись, что можно спокойно прочитать предыдущий фрагмент, пока снизу продолжает накапливаться текст. Затем вернись в конец истории и понаблюдай, как ведёт себя лента при переходе от обычного абзаца к списку и к коду. В узком окне открой длинную строку SQL и прокрути её внутри блока. После завершения найди последние слова ответа и сравни их с содержимым буфера. Такой проход одновременно покрывает динамическое поведение, ширину сообщения и финальную версию Markdown.

### Как описать найденную проблему

Хороший отчёт содержит режим запуска, адрес страницы, ширину окна, действие пользователя, ожидаемое поведение и фактический результат. Если ошибка зависит от конкретного участка ответа, процитируй соседний заголовок или приложи минимальный фрагмент Markdown. Для проблемы во время потока также запиши, проявляется ли она в завершённом ответе. Это позволяет отличить проблему парсинга незавершённого текста от проблемы стилей обычного сообщения. При проверке контейнеров добавь вывод команды состояния и имя сервиса, в логах которого видна первая ошибка.

#### С чего начать прямо сейчас

Если твоя первая задача про UI, открой демонстрационный чат, отправь вопрос из начала инструкции и сравни состояние ленты во время ответа и после его завершения. Если задача про окружение, начни с [файла Compose](https://github.com/pivoslavik/giga-buddy/blob/main/docker-compose.yml) и проверь порядок готовности контейнеров. Для задачи про поиск по материалам посмотри [миграции PostgreSQL](https://github.com/pivoslavik/giga-buddy/tree/main/infra/postgres) и реализацию обработки документов в `ml`. Каждый из этих маршрутов приводит к небольшому набору файлов, который можно прочитать целиком перед первой правкой.

И последнее: сохрани себе минимальный воспроизводимый пример, на котором проверил изменение. Для интерфейса это может быть вопрос в локальном чате, для обработки документов — короткая строка с двумя абзацами, для базы — выборка, которую легко повторить. Такой пример пригодится при следующем обновлении ветки и поможет коллеге проверить результат в том же контексте. Теперь можно переходить к первой задаче в AI Buddy.
